# 인수인계: Ghidra 독립 작업 (집 병렬 트랙, 2026-11-24)

이 문서만 보고 집에서 작업을 시작할 수 있게 적었다. 배경과 판단 근거:

- `docs/ghidra_independence_plan.md` — 계획. 7절이 Astra 협의 결과다.
- `docs/bundle_producer_contract.md` — Bundle 규약. 코드 기준 file:line을 담았다.

## 0. 한 줄 요약

- Ghidra는 **기준 생산자로 유지**한다.
- 집에서는 엔진 코드를 건드리지 않고 **"진단 결과를 만드는 일"**까지만 한다.
- 첫 산출물은 `bundle_lint`와 작은 x86-64 PE 기준 세트다.

## 1. 시작

```

git switch -c home/g0-bundle-lint origin/docs/ghidra-independence
```

이 브랜치는 main 50f28f8 위에 문서 커밋만 얹은 것이다. 엔진 코드는 main과 같다.

### 1.1 기준 커밋을 고정한다 (Astra 설계 리뷰 P1-1)

- G0 기대 판정표에는 **엔진과 exporter의 커밋 SHA**를 함께 적는다.
- 집 브랜치의 엔진(50f28f8)은 S1(`call_fallthrough`)은 읽지만 `proof_input`과 `exception_handlers`는 읽지 않는다. 이 두 필드는
  **G3b-7b 기능 브랜치(7b631de)에만** 있다.
- 그래서 기준표를 두 개 둔다.
  - `main-50f28f8`: 두 필드는 **미지원**으로 판정한다.
  - `g3b7b-7b631de`: 두 필드를 지원한다. 이 표는 그 브랜치가 머지된 뒤에 채워도 된다.
- 계약서(`bundle_producer_contract.md`)의 file:line은 7b631de 기준이다. main에서 다시 확인한다.
- 이렇게 하면 집에서는 엔진 변경이나 아직 머지되지 않은 기능을 기다릴 필요가 없다.

## 2. 환경

| 항목 | 요구 | 이유 |
|---|---|---|
| Ghidra | **12.0.4** 정확히 | 이름 사이드카가 `"12.0.4"`와 `ghidra/GhidraV2CallNaming.java`의 SHA-256에 고정돼 있다 |
| JDK | 21 | Ghidra 12 실행 |
| 실행 위치 | **Linux 또는 WSL** | 엔진의 Bundle 수용(`admit_frozen_bundle`)이 POSIX 전용이다(`O_NOFOLLOW`, `fcntl`). Windows에서는 실패한다 |
| Python | 저장소 venv(테스트 의존성 포함) | 기존 엔진 수용 코드를 그대로 불러 쓴다 |

Bundle은 `tools/bundle_export/export_bundle.py <binary> --ghidra <Ghidra 경로> --output-root <dir> --function-name <이름>`으로
새 import해서 만든다. 사용법은 `tools/bundle_export/README.md`에 있다. 준비된 프로젝트(`--ghidra-project`)로 만든 Bundle에는
증명 사실(S1 등)이 붙지 않으니 기준 세트로 쓰지 않는다.

## 3. 첫 산출물: G0 `bundle_lint` + 기준 세트

### 3.1 `tools/bundle_lint/` (새 디렉터리)

이미 있는 엔진 수용 코드를 **그대로 호출**한다(재구현하지 않는다). 결과는 세 층의 기능별 판정표로 낸다.

1. **운송 / 메모리**
   - manifest / seal의 순서, 크기, 해시, 파일 규칙
   - 블록 플래그와 committed 범위
   - 원본(`original.bin`)과 이미지 매핑
   - image-info 누락, overlay / 중첩 블록
   - 내용을 읽지 않는 필수 멤버(`call-effects`, `call-interface-profile`)는 그 사실을 표시만 한다
2. **연산 / 이름**
   - 행 주소, 길이, flow, exit 교차 규칙
   - varnode 공간과 레지스터 별칭, LOAD / STORE 공간 id, 명령 내부 상대 분기, user-op 번호
   - CALL / RET / INT3 / `rep` / `ud2` 패턴이 Ghidra 모양과 같은지
   - CALL과 꼬리 호출마다 이름 행, ordinal, digest가 맞는지
   - 형식상 유효하지만 엔진이 모르는 opcode(일반 WRITE로 처리됨)를 드러낸다
3. **기능 / 증명**
   - 기능마다 `적용 / 해당 없음 / 보류 / 거부`를 함수, 주소, 이유와 함께 낸다. 기준 엔진이 아예 모르는 필드는 따로 `미지원`으로
     적는다(예: main 50f28f8의 `proof_input` / `exception_handlers`; `해당 없음`과 구별 -- Astra 2차 P3)
   - 함수 거부나 무시된 키가 "전체 성공"에 묻히지 않게 한다
   - S1 / `exception_handlers`에는 생산자, 입력 종류(`proof_input`), 전제를 표시한다

출력 형식은 사람이 읽는 표와 기계가 비교하는 JSON 두 가지로 한다.

### 3.2 기준 세트

- **원본**: 작은 x86-64 PE 하나. testbed 바이너리나 직접 빌드한 작은 C 프로그램을 쓴다. 제3자 바이너리는 쓰지 않는다.
- **기준 Bundle**: 위 원본을 새 import로 내보낸 것 1개.
- **변형 스크립트 3개**: 기준 Bundle을 복사해 조건 하나씩만 바꾼다. 세 변형이 **서로 다른 결과**를 내야 한다.
  1. seal 불일치 → **컨테이너 거부**
  2. CALL ordinal 불일치 → **이름 거부**
  3. 유효한 p-code에서 CALL 패턴만 바꿈(예: x86-64 CALL의 `INT_SUB RSP; STORE; CALL` 순서) → **그 패턴 기능만 미적용**.
     이 경우를 잡아야 "형식만 맞추고 기능을 잃는" 문제를 실제로 검출한 것이다.
- **기대 판정표**: JSON 1개(기준 + 변형 3개의 기대 결과).
- 변형 스크립트는 seal / manifest의 해시를 다시 계산해서 **의도한 조건 하나만** 깨지게 한다.

## 4. 지킬 것

- **`src/tdo_v2`는 수정하지 않는다.** 엔진 쪽 변경이 필요해 보이면 `docs/`에 "제안"으로만 적는다. 엔진 변경은 회사 쪽
  세션에서 게이트와 함께 한다.
- **Bundle, 바이너리, 덤프는 커밋하지 않는다.** 저장소가 공개라서 생성 스크립트, 변형 스크립트, 기대 판정표만 커밋하고,
  생성물은 `.gitignore`로 제외한다.
- 커밋 서명은 기존대로 `김재환2 [rfkjh22]`.
- 같은 Ghidra 버전, 같은 옵션으로 만든 Bundle끼리만 비교한다.
- **힌트를 Bundle에 넣지 않는다** (Astra 설계 리뷰 P1-2). 엔진(U2a)은 `BRANCHIND`의 `flow_targets`가 비어 있을 때만 그 지점을
  "미지 이동"으로 기록한다. 그래서 후보 하나만 넣어도 UNKNOWN이 사라지고, v2는 근거 표시를 무시한 채 그 목적지를 소비한다.
  - 미확정 후보, 함수 소유권 추정, 대체 해독은 **Bundle 밖 진단 파일**에 둔다.
  - v2 Bundle에는 **힌트가 아닌 발견 근거**(entry, export, `.pdata`, 직접 호출 등)가 있는 함수만 넣는다. 힌트로만 발견한 함수는
    따로 떨어진 진단 실행에서만 쓴다 -- v2는 그것에 표시를 붙일 수 없어서, 넣으면 표시 없는 범위 주장이 된다(Fable 2차 P2-2).
    아래 수용 기준도 그 진단 실행에 적용한다.
  - 새 생산자의 v2 출력은 S1(`call_fallthrough`), `exception_handlers`, `proof_input`, Ghidra 생산자 신원(이름 사이드카의
    Ghidra 고정값)을 **빌려 쓰지 않는다**.
  - 수용 기준: 힌트 하나로 새 행을 탐색해도 원래 지점은 UNKNOWN으로 남는다. 그 힌트만으로 요약이 CLOSED가 되거나 간선이
    제거되지 않는다.

## 6. 그다음 집 작업 후보 (순서대로; 모두 "진단까지")

1. **G1 진단 도구**
   - 원본 파일의 섹션표로 Ghidra 이미지 매핑을 검증한다: preferred base, RVA, 크기, zero-fill, 바이트.
   - 버전을 고정한 독립 해독기 **두 개**(XED와 Zydis 또는 iced-x86)를 각각 Intel / AMD 모드로 돌려, 각 행을 원본의 행 시작
     주소부터 해독한다. Ghidra 길이로 자르지 않는다. (소유자 방향 2026-11-24: 이 모듈은 S1 / G3b-7b / RP / pass-through가
     함께 쓰고, 불일치는 사실 보류 + "Ghidra 해독 버그 목록"이 된다. 알려진 Ghidra 버그는 고정한 12.0.4의 `ia.sinc`를 로컬로
     패치하고 패치 id를 Bundle에 기록한다 -- 이것은 회사 쪽 작업이고, 상류 보고는 소유자 승인 뒤에만 한다. 제조사 차이(`66 E8`)는
     버그가 아니라 보류 대상이다.)
   - 유효성, 길이, 직접 / 간접 흐름, 직접 목적지, fallthrough, 복귀 PC를 비교해 **불일치 보고서**를 낸다.
   - 엔진에 반영하는 것(불일치 → S1 보류)은 회사 쪽에서 한다.
2. **좁은 G3 실험**
   - pypcode(SLEIGH)로 x86-64 PE 하나의 p-code를 만들고, 같은 바이너리의 Ghidra Bundle과 **행 단위로 비교**한다:
     opcode, varnode, ordinal, 레지스터 오프셋.
   - pypcode의 `IMARK`를 행 경계로 다뤄야 CALL ordinal과 이름 사이드카가 맞는다.
   - 결과는 비교 보고서까지만 만든다. 새 생산자를 엔진이 정식으로 받으려면 먼저 최소 G2(생산자 식별, 이름 사이드카 고정 해제)가
     필요하고, 그것은 엔진 작업이다.
   - 새 생산자가 `proof_input: "attested-fresh-import-v1"`을 빌려 쓰면 안 된다.

### 6.1 G3는 "라이브러리"로 설계한다 (소유자 방향 2026-11-24; **초안**)

> **초안 (Fable 설계 리뷰 P2-6).** 이 인터페이스는 나중에 정방향 분석기와 인터프리터 분석기가 기대게 될 엔진 쪽 인터페이스다.
> 집에서는 x86-64 PE 시제품을 **비공개 API**로만 만든다. 비교 보고서보다 더 나아간 무언가가 이것에 기대기 전에 Astra / Fable
> 리뷰를 받는다.

G3는 한 번 돌리는 내보내기 도구가 아니라, 나중의 **정방향 분석기**와 **인터프리터 / 가상화 분석기**가 그대로 쓰는 라이브러리로
만든다. Bundle 내보내기는 그 위에 얹는 사용 방법 하나일 뿐이다. 이유와 요구는 아래와 같다.

| 요구 | 왜 필요한가 | 최소 인터페이스(초안) |
|---|---|---|
| 필요할 때 lifting | 정방향 분석 중에 새 코드 주소가 나온다(간접 분기의 실제 목적지, 복호화 / 언패킹된 코드, VM 핸들러). Ghidra 방식은 그때마다 전체를 다시 돌려야 한다 | `lift(space, start, decode_context, byte_source)` → `{row_id, 소비한 바이트 범위, p-code, 길이, flow}` 또는 `{해독 실패 사유}`. `byte_source`는 **바이트 출처 digest**다: 바이트 내용과 그 출처(초기 이미지, 또는 정방향이 만든 복호화 / 언패킹 결과와 그 전제)의 digest. 아래 행 키도 같은 이름을 쓴다 |
| 흐름 그래프를 점점 넓히기 | 값을 계산 → 목적지를 앎 → 간선 추가 → 다시 분석, 의 반복. 인터프리터의 명령 실행 switch가 대표 예 | **라이브러리는 순수하게 둔다**(Fable P2-1): 해독, 구조적 흐름, 로더 상태만 낸다. 고쳐 쓰는 공유 그래프(`add_edge` + `recompute`)는 두지 않는다 -- 철회 = 새 실행(R4)과 결정성에 어긋난다. 간선은 **row_id**와 **전제 id**를 갖고, 소비자가 보는 그래프는 `(기본 그래프, 활성 전제 집합)`의 함수다. 다시 계산하는 정책, 근거 철회, 종속 요약 무효화는 **엔진(TDO)**이 맡는다 |
| 같은 바이트의 여러 해독 | 가상화 / 난독화 도구(VMProtect, Themida 등)는 같은 바이트를 다른 시작점에서 다르게 해독하게 만든다(겹치는 명령, 안티 디스어셈블). Ghidra의 목록은 주소 하나에 명령 하나라 이를 담기 어렵다 | 시작점이 다른 겹친 명령은 주소로 이미 구분된다. 실제 충돌은 **같은 주소·문맥에 초기 바이트와 실행 중 바뀐 바이트가 함께 있을 때**다. 그래서 행 키는 `(공간, 시작 주소, 해독 문맥, 바이트 출처 digest)`이다. 호출자가 준 바이트(복호화 / 언패킹된 코드)는 **출처**를 함께 갖는다 -- 그 자체가 자기 전제를 가진 정방향 값이다. 해독 문맥은 명시 인자다(x86 모드 전환 -- WoW64 / heaven's gate). 해독할 수 없으면 예외 대신 "해독 불가" 결과를 돌려준다. "겹침"도 분석 결과다: 도달한 두 해독 시작점이 충돌할 때 겹침으로 본다. **v2로 내보낼 때 한 갈래를 고르지 않는다**(Fable P2-1): 충돌한 지점이나 함수는 UNKNOWN(U2a 방식)으로 표시하거나 거부하고, 탈락한 해독은 진단 파일에 보고한다 |
| 로드된 이미지 = 정방향 초기 상태 | 정방향 분석은 재배치 / import / TLS / 전역 초기값이 반영된 이미지에서 출발한다 | 로더가 "로드 단계 모델"로 초기 메모리를 만들고, **로드 때 로더가 쓰는 바이트 집합**(과대근사, 로더 메타데이터가 덮일 수 있으면 이미지 전체로 넓힘)을 함께 낸다. **실행 중의 쓰기**(자기 수정 코드, `VirtualProtect` / `mprotect`, 언패커 -- VMProtect / Themida가 바로 이것)는 로더 모델이 아니다: 이름 붙은 전제 `image-code-unmodified-at-runtime`이거나 정방향 분석의 결과다(Fable P2-2) |
| 해독 교차 확인과 연결 | 해독 정확도는 SLEIGH가 정한다(pypcode도 같다) | 각 행에 G1 교차 확인 결과를 붙인다. "일치"는 **무엇을 대조했는지**를 식별해야 한다: 바이트 판, 매핑, 해독기 버전과 모드, 비교한 흐름 속성. 불일치나 미검사는 그 속성에 기대는 사실을 보류한다(Astra 설계 리뷰 P2-5) |
| 발견 범위 보고 | 정방향이 약한 동안 아예 발견되지 않은 함수가 "차이 없음"에 묻히면 안 된다(P2-3) | 시작 후보와 그 출처, 직접 흐름으로 방문한 행, 탐색이 멈춘 지점과 이유. 함수 소유권, 공유 꼬리, 간접 목적지의 완전성은 TDO가 판단한다. **함수 집합은 "관찰 범위" 진술이지 완전성 주장이 아니다**: 없는 함수 / 간선은 "관찰 안 됨"이지 "없음"이 아니다(Fable P1-3). 추측 없는 시작 후보(모두 "발견 근거" 종류로 표시): x64 PE -- entry, export, `.pdata` 시작 RVA, TLS 콜백, CFG 함수 표, 코드에 떨어지는 재배치 목적지(근거일 뿐 증명 아님); ARM64 `.so` -- `.dynsym`, `.init_array` / `.fini_array`, `JNI_OnLoad`, `.eh_frame` FDE(Fable P3) |
| 근거 종류 | 엔진이 각 사실을 어디까지 믿을지 정해야 한다(Fable P2-1) | **닫힌, 버전 있는 열거형**과 각각의 허용 범위: 바이트 / ISA -- 증명에 사용 가능; 정적 구조 -- 사용 가능; 정방향 값 -- 정방향 분석의 전제 아래; 분석가 링크 -- 데이터만(R6); 힌트 -- **절대 불가**. 생산자의 표시는 엔진이 검사할 곳을 안내할 뿐 증명하지 않는다: 엔진은 바이트 근거를 스스로 다시 검사하고(`original.bin`으로 싸게) 다시 검사한 것만 믿는다. 생산자를 믿어야 한다면 `producer:<id>` 전제로 이름 붙인다(Fable P2-3) |

지킬 것:

- 처음 구현은 **x86-64 PE 하나**로 좁힌다. ARM64 ELF(Android .so)는 같은 인터페이스로 그다음에 붙인다.
- **캐시를 분리한다**(Fable P2-4): 생산자 신원(id, lifter 명세 버전, 설정, 입력 종류)이 관측 digest, 템플릿 신원, 링크 /
  stack-scan 캐시 키에 들어가기 전까지는, Ghidra가 아닌 Bundle을 공유 캐시 루트에서 돌리지 않는다. 집 진단은 **따로 떨어진
  캐시 루트**를 쓴다. 지금 파생 템플릿은 생산자를 묶지 않아서, Ghidra로 만든 템플릿이 새 생산자의 Bundle 실행에 그대로
  올라올 수 있기 때문이다.
- G1 해독기는 버전과 라이선스를 고정한다(XED Apache-2.0, Zydis MIT, iced-x86 MIT). 회사 쪽 통합 전까지는 진단 도구의 의존성일
  뿐, 엔진 실행 의존성이 아니다(Fable P3).
- 집에서는 라이브러리와 비교 보고서까지만 만든다. 엔진이 이 라이브러리를 직접 부르게 하는 것(정방향 단계 통합)은 회사 쪽
  설계 리뷰를 거친다.
- Ghidra로도, 이 라이브러리로도 풀리지 않는 것은 분석기가 풀 문제다. 예: 인터프리터 명령 실행 루프 인식, 핸들러 의미 파악,
  바이트코드 해석, 가상화 명령 집합 복원. 이 라이브러리는 그 분석들이 기댈 바닥(해독 / 흐름 / 초기 상태)만 제공한다.

## 7. 판단 기준 (G5 전에 정해 둘 것)

- G4 비교는 두 가지를 **따로** 센다(Astra 설계 리뷰 P2-3): 같은 시작점에서의 해독 비교, 각 생산자가 독립적으로 발견한 범위 비교
- G4는 간접 목적지를 **지운** Ghidra Bundle과도 비교한다(Fable P1-1): 새 생산자는 v2에 구조적으로 정해진 목적지만 내므로,
  "생산자 차이"와 "간접 목적지 복원 차이"를 나눠 보기 위해서다
- **간접 분기 해결 비율**(새 생산자 + TDO 대 Ghidra)을 기준에 넣는다(Fable P1-3). 이것이 없으면 UE DLL에서 G5를 통과할 수 없다
- 큰 바이너리는 분모를 고정한다(P3): 요청한 시작점, 실제로 Bundle에 담긴 함수, v2 한도(Bundle당 함수 4,096개, 전체 512 MiB)
  때문에 빠진 함수를 구분해서, 운송 한도를 "발견 실패"로 세지 않는다
- 같은 SHA와 옵션에서 양쪽에만 있는 함수와 간선
- 누락 / 보류 사유, 이름 해석률, 실제로 제거된 재귀 간선, 실행 시간
- 기존 Ghidra 게이트 변화 = 0, 근거 없는 간선 제거 = 0
- 허용할 정밀도 손실과 기대하는 운영 이득을 **큰 UE DLL로 비교하기 전에** 정해 둔다
